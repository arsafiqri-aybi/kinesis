# Contributing

Keep changes useful to a reader who has no project history. Write documentation as product guidance: purpose, responsibility, inputs, decisions, tradeoffs, checks and outputs. Keep personal conversation, progress reports and temporary validation logs outside the public knowledge tree.

Reuse an existing owner when the responsibility is already covered. A new expertise owner needs a unique ID, operational decision, expected mechanism, failure mode, verification and connected handoffs. Each handoff needs valid endpoints, a condition and a payload. Separate shared capabilities from a client's aesthetic preferences.

Keep rule sources and their graph views consistent. Test project creation, identity isolation, invalid input rejection and graph endpoints after structural changes. Use synthetic fixtures; do not place private client media or credentials in tests.

Document changing provider/platform assumptions with their scope and source. Aesthetic mechanisms remain conditional hypotheses until evaluated in real work. Avoid quality guarantees based solely on static validation.
